# МКР №1: AI-помічник для пошуку й структурування технічної інформації

## 0. План рішення

| Поле | Опис |
|---|---|
| Проблема | Під час навчальних і практичних проєктів (веб-розробка) я постійно шукаю технічні відповіді: порівняння бібліотек, налаштування інструментів, сумісність версій. Це 5–10 разів на тиждень: відкриваю кілька вкладок, читаю документацію й статті, вручну збираю висновки. |
| Поточний процес | 1) гуглю питання; 2) відкриваю 5–8 вкладок; 3) читаю й порівнюю; 4) перевіряю версії; 5) записую висновок у нотатки. Приблизно 15 хв на питання. |
| Дані | Вхід: текстове питання. Зовнішні дані: актуальні веб-сторінки (документація, блоги, GitHub). Вихід: файл Markdown зі структурованою відповіддю і джерелами. |
| Рівень рішення | **Рівень 2 (tools / веб-пошук).** Потрібна актуальна інформація, якої немає «в голові» моделі (версії бібліотек швидко змінюються), тож самого промпту недостатньо. Агент (рівень 3) не потрібен: послідовність кроків відома заздалегідь. |
| Метрика успіху + ціль | (1) Повний час на питання (AI + моя перевірка): з 2 хв до ≤ 5 хв. (2) Частка відповідей, де джерела підтвердили ключові твердження: ≥ 80%. (3) Вартість прогону — $0. |
| Ризики / fallback | Вигадані факти чи посилання → завжди перевіряю ключові твердження за наведеними джерелами. API недоступний → шукаю вручну, як раніше. Повний перелік у розділі 5. |

## Архітектура

```
питання (CLI) ──► research.py ──► DuckDuckGo (пошук) ──► завантаження сторінок (trafilatura)
                       │                                              │
                       │                          LLM Gemini (безкоштовний рівень):
                       │                          відповідь ЛИШЕ за знайденими джерелами
                       │                                              │
                       ├─► evidence/results/NNN-питання.md  ◄─────────┘
                       └─► evidence/runs_log.csv (час, токени, джерела, перевірка)
```

Компоненти: CLI на Python (`argparse`); пошук у DuckDuckGo як зовнішній інструмент; завантаження й очищення тексту
сторінок; виклик LLM API, якому передаються лише пронумеровані джерела; системний промпт, що примушує фіксовану
структуру відповіді (коротка відповідь, таблиця/кроки, ризики) і посилання на номери джерел [1], [2]...;
програма сама додає розділ «Джерела» з реально знайдених URL (модель не вигадує посилань) і позначає ті, де
прочитано лише уривок пошуку; лог запусків у CSV; команди `verify` і `stats` для вимірювання результату.

## Використані AI-технології та інструменти

- LLM Gemini через Google Gemini API (безкоштовний рівень, ключ із Google AI Studio);
- веб-пошук через бібліотеку `ddgs` (DuckDuckGo та запасні пошукові системи, без ключа) і витяг тексту сторінок (`trafilatura`, `requests`);
- Python 3.10+, бібліотека `google-genai`.

## Обґрунтування вибору рівня

| Питання з завдання | Відповідь |
|---|---|
| Вистачає одного промпту? | Ні: потрібна актуальна інформація з інтернету (версії, зміни API), яку модель може не знати. |
| Потрібні зовнішні дані? | Так → **рівень 2**. |
| Потрібен агент (кроки залежать від результатів)? | Ні: сценарій фіксований (пошук → структурування → джерела), модель сама вирішує лише, скільки пошуків зробити. |
| Fine-tuning / власна модель? | Ні: немає ні датасету, ні проблеми, яку не розв'язує промпт із пошуком. |

## 5. Ризики та обмеження

| Ризик | Ймовірність / критичність | Що робити |
|---|---|---|
| AI вигадує факт або неправильно трактує джерело | Середня / висока: помилка може потрапити в курсовий проєкт | Читаю кожне ключове твердження в джерелі, результат позначаю `verify ok/bad`; рахую частку `bad` |
| Джерела застарілі або про іншу версію бібліотеки | Висока / середня | У промпті вимога позначати версійно-залежне; перевіряю версію в документації |
| Веб-пошук повертає SEO-сміття чи форуми замість документації | Середня / середня | Дивлюся на список джерел; для критичних питань перевіряю офіційну документацію |
| Вичерпано ліміти безкоштовного рівня Gemini або API недоступний | Середня / низька | Модель буває перевантажена (503) або дає 429: скрипт тричі повторює запит із паузою, потім перемикається на запасні безкоштовні моделі; якщо недоступні всі — пауза або ручний пошук, як раніше |
| Питання надто вузьке/нове, джерел немає | Середня / середня | Скрипт попереджає «джерел не знайдено — не вважати перевіреним» |
| Невеликі зміни формулювання дають різні відповіді | Середня / низька | Для важливих питань роблю два формулювання і порівнюю |
| Витік API-ключа в репозиторій | Низька / висока | Ключ лише у змінній середовища, не в коді; `.env` не комітити |
| DuckDuckGo тимчасово обмежує запити або сторінка не завантажується | Середня / низька | Скрипт по черзі пробує кілька пошукових систем (DuckDuckGo, Brave, Yahoo, Mojeek, Startpage); для недоступних сторінок бере лише уривок і позначає це в джерелах |

## 6. Реальне використання (протокол)

Збір даних проходив 26.11.2026: 10 запитів до скрипту. Через дедлайн усе зібрано за один день, тому тест не охоплює довшого періоду, і це обмеження. Перші 5 питань — реальні задачі з моїх навчальних проєктів, для яких я спершу сама шукала відповідь із таймером і передавала час через `--manual-min`. Решта 5 питань
(№6–10) оброблялися лише зі скриптом, тож для них порівняння «до» немає. Для кожного запиту:

1. Для питань 1–5 спершу шукаю відповідь вручну й записую хвилини (`--manual-min`).
2. Запускаю `ask`, потім перевіряю 2–3 ключові твердження в джерелах і виконую `verify ID ok|bad --check-min N`.

Докази лежать у `evidence/`: `runs_log.csv`, `results/*.md`, скріншоти терміналу.

## 8. Відповіді на питання

1. **Яку проблему ви вирішували?** 
Повільний і розпорошений пошук технічної інформації для навчальних проєктів.

2. **Чому вона реальна й корисна для автоматизації?** 
Повторюється щотижня, кожного разу однотипні кроки (гугл → вкладки → порівняння → нотатки). Для тестування я брала реальні задачі зі своїх проєктів (захист маршрутів і Edge Runtime у NextAuth v5, Prisma і Neon, версії Prisma, Tailwind v4): на пошук відповіді на кожну з них я витрачала від 11 до 19 хвилин.

3. **Як задача виконувалась до AI?** 
Ручний пошук у браузері та конспектування, у середньому 14,6 хв на питання (за 5 вимірами).

4. **Яке AI-рішення побудували?** 
CLI-скрипт, що через LLM з веб-пошуком видає структурований Markdown із джерелами та веде лог метрик.

5. **Чому саме цей рівень?** 
Потрібна актуальна зовнішня інформація (рівень 2), а фіксований сценарій не вимагає агента; див. розділ «Обґрунтування вибору рівня».

6. **Які альтернативи розглядали?** 
Чат-бот без пошуку (рівень 1; застаріла інформація), платний LLM із вбудованим пошуком (дає схожий результат, але не безкоштовний), персональний RAG по власних нотатках (не покриває нові питання), агент із багатьма кроками (надмірно складно).

7. **Які моделі й інструменти?** 
Gemini (безкоштовний рівень Gemini API), DuckDuckGo через `ddgs`, `trafilatura`, Python, `google-genai`.

8. **Які проблеми або помилки виникли?**
   - **Перевантаження моделі (503 UNAVAILABLE).** Під час першого тестового запуску основна модель відповідала «This model is currently experiencing high demand»; той запуск тривав 267 с, із них близько 90 с пішло на очікування. Рішення: скрипт тричі повторює запит із паузою 15 с і перемикається на запасні безкоштовні моделі. Пізніше 503 ще раз з'явилась у питанні 3 (+15 с).
   - **Збій пошуку («No results found»).** Із 11 викликів `ask` у зборі даних у 2 (питання про Neon і про junior frontend) жодна пошукова система не повернула результатів, і запит довелося повторити через хвилину. Рішення: скрипт перебирає кілька пошукових систем (DuckDuckGo, Brave, Yahoo, Mojeek, Startpage); у всіх успішних запусках результати дала Yahoo.
   - **Неповне читання джерел.** Зі 6 знайдених джерел скрипт повністю читає лише 3–4 (решта лише уривок із пошуку), тому твердження з таких джерел перевіряю окремо; у результатах вони позначені.
   - Відповідей зі статусом `bad` не було: у перевірених 2–3 ключових твердженнях кожної відповіді розбіжностей з джерелами я не знайшла.

9. **Наскільки надійне рішення?** 
Усі 10 відповідей отримали `ok` (10 з 10, 100%), але це вибіркова перевірка: я перевіряла 2–3 ключові твердження кожної відповіді, а не кожне слово, тому показник означає «ключові твердження підтвердилися», а не «відповідь безпомилкова». Вибірка невелика (10 запитів), а питання про версії бібліотек швидко старіють, тож результат треба перевіряти щоразу. Економія часу також трохи завищена: перевірка джерел поверховіша за повний ручний пошук. Рішення прискорює пошук, але не замінює перевірку джерел.

10. **Що змінилося після впровадження?** 
Питання, на які раніше йшло 11–19 хв, тепер займають приблизно 4–5 хв разом із перевіркою, а сама відповідь готується за 18–41 с. Я більше не збираю відповідь із кількох вкладок вручну, а перевіряю вже структуровану відповідь за посиланнями.

11. **Скільки часу чи ресурсів заощаджено?** 
≈ 10 хв на питання: на 5 вимірюваних питаннях з 73 до 23 хв, тобто 50 хв (≈ 68%). Грошей рішення не коштує: безкоштовний рівень Gemini API і безкоштовний пошук.

12. **Що змінили б надалі?** 
Додати пріоритет офіційній документації (обмеження доменів пошуку), кешування однакових запитів, режим «порівняння версій», зберігання результатів у пошуковій базі нотаток.
